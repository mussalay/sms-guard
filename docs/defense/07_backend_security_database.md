# 07. Backend, безопасность и база данных

## HTTP, REST и FastAPI

HTTP — протокол запроса/ответа. REST — подход к представлению ресурсов через URI и методы, а не требование «любой JSON является REST». GET читает, POST создаёт/выполняет операцию, DELETE удаляет. JSON — текстовый формат объектов/массивов. HTTP200 означает успешную обработку запроса, а не правильность ML-классификации.

FastAPI регистрирует функции декораторами `router.get/post/delete`. Dependency injection — внедрение зависимостей — означает, что `Depends` получает пользователя, сессию SQLAlchemy и проверяет CSRF до выполнения обработчика. `Request` даёт тело/headers/cookies. Здесь входные JSON читаются вручную в `data/perform`, а не через отдельные Pydantic body-схемы; это объясняет неполный requestBody в OpenAPI. Типизированный `HealthResponse` существует отдельно.

Асинхронная функция `async def` позволяет ожидать I/O через await, но **не превращает синхронный ML или SQLAlchemy в неблокирующий код**. В async perform CPU inference исполняется синхронно. Для локального single-worker это работает; устойчивую конкурентную нагрузку не измеряли. Не говорить «FastAPI автоматически распараллелил модели».

| Ресурс | Метод/путь | Защита и результат |
|---|---|---|
|Состояние|GET `/api/v1/health/`|Без входа,200, liveness и bool моделей|
|Регистрация|POST `/api/v1/auth/register/`|CSRF;201 или 400 duplicate/invalid|
|Вход|POST `/api/v1/auth/login/`|CSRF;200/401/429|
|Выход|POST `/api/v1/auth/logout/`|Сессия+CSRF;204 без тела|
|SMS/URL|POST `/api/v1/check/sms/`, `/url/`|Сессия+CSRF;200/400/429/503|
|Список/деталь|GET `/api/v1/checks/`, `/{id}/`|Сессия, owner-only, чужая 404|
|Удаление|DELETE `/api/v1/checks/{id}/`|Owner+CSRF;204|
|Статистика|GET `/api/v1/stats/summary/`|Личная; all только staff, без чужого текста|
|Профиль|GET/POST `/api/v1/profile/`|Сессия; изменение CSRF, пароль проверяет текущий|

400 — плохие входные данные,401 — нет действительной авторизации,403 — проверка безопасности не пройдена,404 — объект не найден/чужой,429 — лимит,503 — сервис модели недоступен. Два обработчика app/main.py приводят HTTP/validation errors к `error:{code,message}`. Общего JSON-handler для неожиданных 500 нет. Swagger перечисляет пути, но тела анализа не описаны полностью; таблица README не делает контракты типизированными.

## Пароль, соль, сессия

`hash_password` создаёт случайную соль 16 байт и PBKDF2-HMAC-SHA256 с 600000 итераций. Итерации намеренно делают вычисление дорогим для перебора; соль не секрет, она устраняет одинаковые хеши одинаковых паролей и мешает заранее рассчитанным таблицам. Это **хеширование, не шифрование**: пароль не восстанавливается ключом. `verify_password` извлекает параметры, считает digest и сравнивает `hmac.compare_digest`, уменьшая утечку по времени сравнения. Быстрый SHA256 для пароля был бы плохим выбором.

Сессионный token — криптографически случайная непрозрачная строка, а не JWT. Cookie содержит token, БД содержит его SHA256: для случайного высокоэнтропийного token быстрая хеш-функция допустима. AuthSession хранит user_id и expires_at, срок 12 часов. Logout удаляет строку; смена пароля отзывает все сессии пользователя. `current_user` проверяет хеш cookie и срок; пароль в запросах анализа не передаётся.

Cookie HttpOnly запрещает обычное чтение JS, SameSite=Lax ограничивает межсайтовую отправку, Secure ставится для HTTPS. Secure-cookie не посылается по HTTP. На локальном HTTP Secure не выставляется. HttpOnly не предотвращает все действия XSS, а только чтение cookie; поэтому нужен безопасный вывод текста. О paque sessions не требуют подписи `secret_key`: поле настроек сейчас фактически не используется для подписания сессии.

После пяти неправильных входов пауза 60 секунд для пары IP+username;30 анализов/мин на user. Счётчики в памяти, после restart сбрасываются и между workers не разделяются. Это ограничение реализации, а не глобальная защита от распределённого перебора.

## Три разных вида атак

**CSRF** — подделка запроса от имени вошедшего пользователя с чужого сайта. В cookie `sg_csrf` хранится случайная строка, шаблон выводит её в meta, `api()` переносит в `X-CSRF-Token`; сервер сравнивает cookie/header в постоянное время. Это double-submit, то есть подтверждение токена в двух каналах. Регистрация/вход/выход и изменения защищены. SameSite — дополнительная мера, не замена CSRF.

**XSS** — выполнение внедрённого скрипта в браузере. Jinja2 экранирует HTML; JavaScript создаёт узлы и задаёт textContent, не innerHTML. URL результатов не делают href. Текст `<script>alert(1)</script>` должен быть текстом. Вставка текста через JSON сама по себе XSS не решает: важен конечный способ вывода в DOM.

**SQL injection** — изменение смысла SQL через ввод. SQLAlchemy строит параметризованные выражения, например `Check.user_id == user.id`; строка `' OR 1=1 --` не становится оператором. ORM не является магическим запретом инъекций: ручная конкатенация SQL всё равно опасна, в проверяемых местах её нет.

**SSRF** — принуждение сервера обращаться к введённому адресу. Здесь URL — только строка; urllib.parse разбирает, ipaddress проверяет, tldextract использует встроенный PSL без загрузки, RF анализирует числа. Даже IP/внутренний адрес не открывается. Официальные загрузчики обучающих наборов — отдельный контур с фиксированными источниками, не endpoint проверки URL.

## Семь таблиц и транзакция

| Класс app/db/models.py | Назначение | Основные связи/ограничения |
|---|---|---|
|User|логин/email/солёный хеш/staff|Уникальные username/email|
|UserProfile|согласие и preferred_language|1:1, по умолчанию consent=false|
|AuthSession|хеш token, expiry|Много на User; FK cascade|
|Check|ввод, mask, язык, score, P, объяснение, версии, payload|FKuser; unique(user_id, request_key); индексы user/date и category|
|UrlResult|адрес/домен/P/категория/features|FKCheck, каскад|
|DetectedFeature|код группы/название/вес|FKCheck, каскад|
|ModelVersion|тип/версия/алгоритм/метрики/порог/active|Справочник; Check содержит строки версий, а не FK на эту таблицу|

Session SQLAlchemy — единица работы с БД, не HTTP-сессия. `flush` выдаёт Check.id до commit, дочерние строки используют этот ID; `commit` фиксирует всё вместе. При IntegrityError выполняется rollback; совпавший idempotency key позволяет вернуть существующий результат. Unique constraint защищает от двух одинаковых вставок в БД, простая проверка до вставки сама по себе гонку не исключает.

Foreign key — внешний ключ: гарантирует существование родителя. Cascade deletion удаляет URL/признаки вместе с Check. SQLite требует `PRAGMA foreign_keys=ON`, это включается при подключении. Индекс ускоряет поиск, но занимает место и удорожает запись; индекс user/date подходит истории пользователя по времени.

Без согласия `input_text=NULL`, `input_masked` скрывает телефон/карту 13–19 цифр/сумму. Остальные слова могут содержать персональные данные; это маскирование, не полная анонимизация. Согласие влияет на новые проверки; не восстанавливает ранее скрытые значения. Полные standalone URL и параметры требуют осторожности: URL могут содержать чувствительную информацию, особенно при переносе результатов.

## Alembic, история и статистика

Alembic — версии схемы, а не история пользовательских SMS. `upgrade()` миграции создаёт 7 таблиц, `downgrade()` удаляет в обратном порядке. `migrations/env.py` передаёт Base.metadata и URL соединения. `python -m app` вызывает upgrade head; lifespan дополнительно делает create_all. Последнее создаёт отсутствующие таблицы, но не заменяет миграции изменения схемы. В тренировке не выполнять downgrade на рабочей БД.

`history/detail/remove/clear_history` всегда ограничивают user_id. Недостаточно скрыть кнопку чужой записи: проверка обязательна на сервере. Администратор получает агрегаты, а не чужой текст. Пагинация 20, фильтры type/category/level/date, сортировка date/id; JS хранит фильтры в адресной строке. Долг: таблица не выводит отдельную колонку risk_level.

`stats` использует SQL COUNT, GROUP BY, AVG, date и join DetectedFeature: агрегация выполняется в БД, Python только формирует JSON. Chart.js рисует category/days/top5/levels. Последние 10 — личные, при admin all recent пуст; ModelVersion даёт активные метрики. APIbenchmark1000 стр≈.021 с не доказывает время полной отрисовки браузером.

## Как объяснять тестирование

Unit test проверяет малую функцию, integration test — совместную работу слоёв. Здесь normalize/risk/features — модульные, TestClient+SQLite+модели — интеграционные. Fixture создаёт окружение теста; parametrization запускает одну проверку на разных входах; monkeypatch временно заменяет поведение, например блокирует DNS. Coverage измеряет выполненные строки, а не правильность всех решений.

Факты последнего аудита:114 passed,78%общего, ML≈71%, risk98%, Ruff чисто, миграция с нуля прошла. Это исторический запуск аудита, не новый запуск подготовки материалов. После security-тестов не утверждать «уязвимостей нет»: нет полноценного пентеста, общих limiter между процессами или полного контракта 500.

## Как читать Python этого проекта

`def` определяет функцию, `class` — класс. Аннотация типа описывает ожидаемый контракт, но не проверяет произвольный Python-вызов автоматически. `list` — изменяемый список, `tuple` — кортеж, `dict` — словарь ключ→значение, `set` — множество уникальных значений, `None` — отсутствие значения. Dataclass AnalysisResult автоматически получает удобный конструктор полей; `asdict` превращает его в словарь для ответа.

Декоратор `@router.post` регистрирует обработчик; `@lru_cache` запоминает результат загрузки store по аргументам. `self` — экземпляр класса, не глобальная переменная. Comprehension — компактное создание коллекции, например списка сработавших групп. Контекстный менеджер `with` обеспечивает завершение работы с ресурсом; dependency `db` с yield выдаёт SQLAlchemy Session и закрывает её после обработки.

Исключения разделяют ошибки входа и недоступность: ValueError превращается в400, RuntimeError отсутствующей модели —503, IntegrityError означает конфликт ограничения БД. Это конкретные обработанные случаи, не гарантия JSON для всех неожиданных исключений. `async/await` — управление ожиданием, не автоматическое ускорение CPU-bound вычислений.
