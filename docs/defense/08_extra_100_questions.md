# 08. Сто дополнительных вопросов преподавателя

Это авторские учебные вопросы, **не вопросы из PDF**. Нумерация 1–100, группы 30/40/30. Краткий ответ полезен для устного начала, подробный — для обоснования; проверяйте код по 03, формулы по 04/05 и ограничения по 09.

## Базовые:1–30

### 1. Что решает SMS Guard?

**Кратко.** Оценивает признаки spam, фишинга и социальной инженерии в SMS и URL.

**Подробно.** Результат рекомендательный: модели, правила и эвристический риск не дают гарантии безопасности. Показать новый ввод, объяснение, историю и предупреждение. Не подменять задачу «доказать преступление» статистической классификацией.

### 2. Чем spam отличается от fraud?

**Кратко.** Spam — нежелательная рассылка; fraud — мошеннический обман.

**Подробно.** Рекламное сообщение может быть spam без кражи денег. UCI содержит ham/spam, поэтому высокая метрика SMS не доказывает распознавание всех мошеннических схем. Это ограничение целевой разметки.

### 3. Что такое smishing?

**Кратко.** Фишинг через SMS или похожие текстовые сообщения.

**Подробно.** Обычно сочетает предлог банка/доставки, психологическое давление и просьбу сообщить код либо открыть ссылку. Ссылки может не быть: запрос секретного кода всё равно опасен. Поэтому нужна текстовая ветка.

### 4. Какие технологии использованы?

**Кратко.** Python3.13, FastAPI, SQLAlchemy, SQLite, Jinja2, Bootstrap, scikit-learn, Chart.js.

**Подробно.** FastAPI обслуживает HTTP, SQLAlchemy связывает объекты с БД, Jinja2 создаёт HTML, JS вызывает API, scikit-learn применяет модели. Alembic версионирует схему; pytest и Ruff проверяют поведение и стиль.

### 5. Что такое frontend?

**Кратко.** Часть приложения, с которой взаимодействует браузер пользователя.

**Подробно.** Шаблоны HTML, CSS и static/js/app.js рисуют формы/результаты. JavaScript отправляет fetch, но не обучает модели. Нельзя доверять только браузерным ограничениям длины: сервер повторно проверяет ввод.

### 6. Что такое backend?

**Кратко.** Серверная обработка запросов, моделей, авторизации и хранения.

**Подробно.** app/main.py создаёт FastAPI, app/web.py содержит маршруты, services.py объединяет анализ. Браузер не получает прямой доступ к SQLite и joblib; обращается через защищённые endpoints.

### 7. Как работает API?

**Кратко.** Браузер отправляет HTTP-запрос, сервер проверяет его и возвращает JSON.

**Подробно.** Например POST check/sms получает text, вызывает анализ и сохраняет результат. HTTP200 означает успех обработки, не истинность прогноза. Ошибки входа/сессии/лимитов/модели имеют разные коды.

### 8. Где находятся endpoints?

**Кратко.** В app/web.py; health отдельно в app/api/v1/health.py.

**Подробно.** Искать @router.post/get/delete. app/main.py подключает routers. Пакеты accounts/dashboard сами по себе не содержат отдельной реализации маршрутов: нельзя показывать пустой __init__ как доказательство функциональности.

### 9. Где именно обучается SMS-модель?

**Кратко.** В ml/sms_experiment.py:fit_candidates.

**Подробно.** make_model только создаёт estimator. fit_candidates вызывает model.fit для SVM и classifier.fit для NB/LR на train; select выбирает, finalize оценивает test. Эти функции не вызываются при пользовательском запросе.

### 10. Где находится NLP?

**Кратко.** В ml/preprocessing.py и ml/features.py.

**Подробно.** normalize_sms очищает и заменяет сущности; SmsNormalizer входит в pipeline, TfidfVectorizer превращает текст в числа. Runtime-словарь social.py дополняет ML, а не заменяет нормализацию внутри сохранённой модели.

### 11. Где используется TF-IDF?

**Кратко.** В build_feature_pipeline из ml/features.py.

**Подробно.** Word-ветка использует униграммы/биграммы, char_wb — символы 3–5. Fit учит vocabulary/IDF на train, predict только transform. Нельзя заново fit на введённом пользователем SMS.

### 12. Что такое 59924 признака?

**Кратко.** Это число столбцов одного SMS-вектора, не число сообщений.

**Подробно.** 8785 word+51133 char+6 manual; X_train имеет 3594 строки. Большинство значений нулевые, поэтому матрица разреженная. Число обученных коэффициентов зависит от estimator,59924 — размер входного представления.

### 13. Какие классы у SMS-модели?

**Кратко.** 0=ham,1=spam.

**Подробно.** В интерфейсе есть общий риск SAFE/SUSPICIOUS/FRAUDULENT, но это не три обученных SMS-класса. Он объединяет вероятность, словарь и URL. Не приписывать матрицу SVM комбинированному Risk Score.

### 14. Какой датасет SMS?

**Кратко.** Официальный английский UCI SMS Spam Collection.

**Подробно.** 5574 исходных сообщения,5135 после удаления повторов, train/val/test3594/770/771. Паспорт фиксирует источник, CC BY4.0, дату и hash. Русский корпус отдельно, только для тестирования правил+URL.

### 15. Какой датасет URL?

**Кратко.** PhiUSIIL UCI967, использовано 50000 URL.

**Подробно.** Из исходных 235795 очищены некорректные/повторы/конфликты, затем сделана стратифицированная подвыборка. Только URL, label, без готовых HTML-признаков. Для обучения источниковые 1 legitimate/0 phishing инвертируются.

### 16. Что такое train/validation/test?

**Кратко.** Части для обучения, выбора и итоговой независимой оценки.

**Подробно.** Train учит параметры и vectorizer, validation выбирает алгоритм/порог, test используется однократно после фиксации. Тестовый результат уже известен, поэтому новый подбор по нему нарушит протокол.

### 17. Что такое Data Leakage?

**Кратко.** Утечка информации проверочной части в обучение или выбор решения.

**Подробно.** Примеры: одинаковый SMS в train/test, общие URL-домены, IDF на всём корпусе, порог по test. В проекте сохранены split и guards; корректность нужно объяснять потоком данных, а не только наличием claim-файла.

### 18. Почему именно SVM?

**Кратко.** Она дала наибольший validation F2 среди сравниваемых алгоритмов при P≥.85.

**Подробно.** Выбрана calibrated Linear SVM C10. Это вывод данного эксперимента, не универсальное превосходство SVM. Самая высокая Precision у NB не сделала её победителем: приоритет задан F2 с допустимой Precision.

### 19. Как работает Random Forest?

**Кратко.** Усредняет ответы множества деревьев решений.

**Подробно.** Bootstrap и случайный выбор признаков уменьшают зависимость деревьев. Наш RF имеет 150 деревьев, depth12,22 URL-признака. Вероятность — средняя доля positive по листьям деревьев, а не правило «ссылка содержит login».

### 20. Как рассчитывается Risk Score?

**Кратко.** Взвешиваются доступные SMS/URL-вероятности и группы правил, затем применяются минимальные границы.

**Подробно.** compute_risk: веса.5/.3/.2, S=min(k/3,1), нет компонента — исключён её вес. CODE_REQUEST≥70, сильные две модели≥85, IP/brandPuny≥60. Для standaloneURL дополнительное отображение пороговых диапазонов.

### 21. Почему модель может ошибаться?

**Кратко.** Данные ограничены, признаки не отражают весь смысл, будущие сообщения отличаются от обучающих.

**Подробно.** Есть шум меток, близкие безопасные/опасные формулировки, смещение источника и смена распределения. Вероятность не гарантирует истину. Ошибки оценивают на независимом корпусе, а не скрывают исключениями для примеров.

### 22. Почему Accuracy недостаточно?

**Кратко.** На дисбалансе можно часто отвечать большинством и пропускать все угрозы.

**Подробно.** Всегда ham на очищенном UCI даёт≈.88 Accuracy, но Recallspam0. Поэтому показываем Precision, Recall, F1, F2, CM, ROC/PR и реальную цену ложных тревог.

### 23. Почему русский язык обрабатывается иначе?

**Кратко.** Нет русского обучающего корпуса для SMS ML.

**Подробно.** Кириллица переводит анализ в правила+URL с P_sms=null и предупреждением. Recall.66 на 100 искусственных русских SMS — результат этой ветки, не английской модели и не подтверждение надёжной русской поддержки.

### 24. Что произойдёт при новом неизвестном SMS?

**Кратко.** Он пройдёт фиксированный pipeline и получит прогноз по известным признакам.

**Подробно.** Неизвестные n-граммы игнорируются; char/manual могут сработать. Модель не добавляет словарь и не переобучается. Совершенно новый стиль может дать уверенную ошибку, поэтому есть предупреждение.

### 25. Почему используется SQLite?

**Кратко.** Для локального проекта нужен простой файловый запуск без отдельного сервера БД.

**Подробно.** SQLAlchemy даёт ORM, Alembic — миграции. SQLite подходит демонстрации и умеренной нагрузке, но конкурирующие записи ограничены. Заявление о production-масштабе потребовало бы других измерений и инфраструктуры.

### 26. Как защищаются пароли?

**Кратко.** PBKDF2-SHA256 с солью и 600000 итераций, plaintext не хранится.

**Подробно.** security.py создаёт новую соль на пароль, хранит алгоритм/итерации/соль/digest и сравнивает compare_digest. Это не обратимое шифрование. Сессионный token отдельно случайный и хранится в БД как SHA256.

### 27. Что будет при отсутствии файла модели?

**Кратко.** Приложение может стартовать, соответствующий анализ ответит 503.

**Подробно.** ModelStore оставляет отсутствующий classifier None; health показывает false, inference бросает RuntimeError, perform переводит её в понятную ошибку. Повреждённый joblib — отдельный случай, не полностью проверенный отсутствием файла.

### 28. Как работает Dashboard?

**Кратко.** Читает SQL-агрегаты из stats API и строит Chart.js графики.

**Подробно.** Counts/avg/groups/dates считаются в БД, JS рисует категории, динамику, top5 иуровни. Периоды 7/30/90, личный scope; staffall безчужихтекстов. Обновление при открытии страницы, непостоянный push.

### 29. Где хранится история?

**Кратко.** В SQLite, основной класс Check в app/db/models.py.

**Подробно.** Основная таблица Check связана с User, UrlResult и DetectedFeature через внешние ключи. Без согласия сохраняется маскированный вариант, а input_text равен NULL. API ограничивает выборку владельцем; скрытие чужих кнопок не заменяет серверную проверку.

### 30. Почему полностью выполнены только 8 из 18?

**Кратко.** Работающий MVP не закрыл все строгие критерии и доказательства PDF.

**Подробно.** Частичными признаны задания 2,7,8,11,13–18. Есть конкретные долги: перенос моделей, baseline-разбор, CV и ablation, качество URL, полнота объяснений, API-контракты, UI и формальный комплект. Это не означает отсутствие десяти модулей: функционирование и полная приёмка различаются.

## Технические:31–70

### 31. Что делает NFKC и чего не делает?

**Кратко.** Приводит совместимые Unicode-формы к общему виду; не переводит визуально похожую кириллицу в латиницу.

**Подробно.** Полноширинные символы приводятся к совместимой форме, затем выполняется lower. Кириллическая «а» и латинская «a» не становятся одной буквой. Нормализация SMS не заменяет IDNA и обнаружение визуально похожих доменов; в коде это разные операции.

### 32. Почему URL заменяется раньше чисел?

**Кратко.** Чтобы цифры адреса не разрушили его до извлечения сущности.

**Подробно.** Если сначала заменить числа, адрес с IP или query-параметрами может перестать распознаваться. normalization_steps обрабатывает email, URL, суммы, телефоны и остальные числа в определённом порядке. Тесты проверяют пересечения и границы сущностей.

### 33. Какая токенизация реально используется?

**Кратко.** NLTK RegexpTokenizer при опциональных стоп-словах; TF-IDF имеет собственные анализаторы.

**Подробно.** NLTK RegexpTokenizer работает в ветке опционального удаления стоп-слов. Word TF-IDF использует token_pattern, char_wb строит символьные фрагменты. Нельзя считать, что один NLTK tokenizer управляет всеми признаками; текущая модель оставляет стоп-слова.

### 34. Как вычисляется TF-IDF?

**Кратко.** Частота термина умножается на редкость по документам, затем нормируется.

**Подробно.** В word-ветке tf=1+ln(count), idf=ln((1+N)/(1+df))+1, затем L2-нормировка. N и df определены только train. В char-ветке sublinear_tf не задан и остаётся False. Числовой расчёт есть в 05.

### 35. Что означают min_df2 и max_df.95?

**Кратко.** Отбрасываются термины менее чем в двух документах и более чем в 95%train-документов.

**Подробно.** df — число документов, содержащих термин, а не общее число его повторов. min_df2 исключает термины только одного train-документа, max_df.95 исключает почти повсеместные. Изменение этих параметров по результатам test нарушило бы протокол.

### 36. Почему char_wb, а не только слова?

**Кратко.** Частичные фрагменты слов могут пережить опечатку.

**Подробно.** Опечатка разрушает лишь некоторые фрагменты слова, поэтому часть сигнала сохраняется. char_wb строит фрагменты внутри слов с padding, длины 3–5. Но независимый эффект char-ветки в проекте не измерен ablation, и произвольную обфускацию она не гарантирует распознать.

### 37. Зачем FeatureUnion?

**Кратко.** Соединяет параллельные word, char, manual признаки одного объекта.

**Подробно.** FeatureUnion соединяет столбцы word, char и manual для тех же строк. Он не усредняет ответы трёх моделей. Pipeline, напротив, задаёт последовательность шагов. После объединения ручные признаки могут иметь иной масштаб, поэтому линейные модели используют scaler.

### 38. Почему uppercase берётся из raw?

**Кратко.** После lower регистр был бы утрачен.

**Подробно.** lower уничтожил бы информацию о заглавных буквах. ManualSmsFeatures считает её по raw, но наличие сущностей — по нормализованному тексту. Если букв нет, доля устанавливается в 0: это защищает от деления на нулевой знаменатель.

### 39. Почему sparse нельзя бездумно превратить в dense?

**Кратко.** Память растёт как число строк×число столбцов.

**Подробно.** Плотная train-матрица 3594×59924 float64 потребовала бы примерно 1.72 GB только для значений. CSR хранит ненулевые элементы, индексы и границы строк. NB, LR и LinearSVC совместимы с sparse;22 URL-признака удобно хранить плотной матрицей.

### 40. Почему MaxAbsScaler для SMS?

**Кратко.** Масштабирует ручные значения и не центрирует sparse.

**Подробно.** MaxAbsScaler делит координаты на train-максимумы модулей, не вычитая среднее; нули остаются нулями. Центрирование StandardScaler разрушило бы sparse. В URL-эксперименте 22 dense-признака, поэтому StandardScaler допустим. NB получает неотрицательный X без такого центрирования.

### 41. Как alpha влияет на NB?

**Кратко.** Сглаживает частоты, предотвращая нулевые вероятности признаков.

**Подробно.** Сглаживание оценивает вероятность как (count+alpha)/(total+alpha·d). Оно не даёт одному отсутствующему признаку занулить правдоподобие класса. Сравнивались.1/.5/1; baselinealpha1 и лучший NBalpha.1 — разные объекты, их нельзя смешивать.

### 42. Что означает C у LR и SVM?

**Кратко.** Параметр, связанный с обратной силой регуляризации.

**Подробно.** Большее C обычно ослабляет регуляризацию, позволяя весам сильнее подстроиться под train. У LR и SVM разные функции потерь, одинаковое C не означает одинаковое поведение. Значения выбраны на validation; правила «всегда C10» нет.

### 43. Почему LinearSVC не выдаёт вероятность?

**Кратко.** Оптимизирует margin-loss, а не вероятностную модель напрямую.

**Подробно.** decision_function возвращает линейный margin w·x+b, масштаб которого не равен вероятности. Sigmoid-калибратор учит отображение по OOF margins. Просто применить произвольную сигмоиду без обученных коэффициентов — не то же, что проверенная калибровка.

### 44. Как работает ensemble=False у калибратора?

**Кратко.** Один калибратор учится на OOF оценках, базовый estimator затем учится на всём train.

**Подробно.** Калибратор получает объединённые OOF оценки, затем базовый estimator обучается на всём train. При inference используются этот estimator и калибратор. FeatureUnion и scaler находятся внутри estimator, чтобы каждый fold не видел vocabulary своей проверочной части.

### 45. Как выбирается порог SMS?

**Кратко.** Перебором validationP с ограничением Precision≥.85 и максимумом F2.

**Подробно.** choose_threshold перебирает уникальные validation probabilities и 0/1. Условие — Precision≥.85, главный критерий — F2, затем Recall и Precision. В полном равенстве max(tuple) выбирает больший порог; это отличается от буквального «минимальный порог» в PDF.

### 46. Как считается F2 из матрицы?

**Кратко.** F2=5 TP/(5 TP+4 FN+FP).

**Подробно.** Для SMS TP88, FN5, FP6: F2=5·88/(5·88+4·5+6)=.944206. TN не входит в формулу. β=2 даёт β²=4 в весах, но не означает универсальную денежную стоимость пропуска или удвоение F1.

### 47. Чем PR-AUC отличается от AP?

**Кратко.** В проекте PR-AUC — трапеции, AP — ступенчатая сумма приростов Recall×Precision.

**Подробно.** metrics вызывает auc для PR-кривой и average_precision_score отдельно. Первая метрика использует трапеции, вторая — сумму Precision по приростам Recall. Разная интерполяция даёт разные числа; в отчёте их определения нужно сохранять.

### 48. Зачем URL делить по доменным группам?

**Кратко.** Чтобы модель не проверялась на знакомых доменах под новыми путями.

**Подробно.** Иначе одинаковый домен мог бы попасть в train и test под разными путями. registrable_domain учитывает PSL и объединяет поддомены. GroupShuffleSplit сохраняет группы целиком, поэтому доли строк отличаются от долей групп; тест проверяет все три попарных пересечения.

### 49. Почему URL source labels инвертируются?

**Кратко.** В PhiUSIIL1 означает legitimate, а в проекте 1 должно означать phishing.

**Подробно.** В источнике 1 означает legitimate, тогда как positive class проекта — phishing. Выражение 1-label согласует метрику, predict_proba[:,1] и интерпретацию риска. Без инверсии высокая вероятность могла бы ошибочно трактоваться как опасность, хотя означала легитимность.

### 50. Как RF выбирает ветвь дерева?

**Кратко.** Сравнивает одну координату с порогом на каждом узле.

**Подробно.** При inference каждый узел сравнивает координату с обученным порогом и направляет объект дальше. Лист даёт долю positive, лес усредняет 150 деревьев. Во время fit разбиения уменьшают Gini; это обученная структура, а не вручную заданный список опасных слов.

### 51. Какие 22 URL-признака используются?

**Кратко.** Структурные длины/счётчики, IP/порт/схема, маскировка, словарь и энтропия.

**Подробно.** Порядок задаёт FEATURE_NAMES: длины и счётчики, IP/HTTPS/порт, @ и двойной слеш, сокращатель, слова, Punycode, смешение букв, бренд, энтропия, TLD и параметры запроса. Модель видит числа из строки, не содержимое страницы или реальную репутацию сайта.

### 52. Зачем scheme/www нормализуются?

**Кратко.** Чтобы одинаковые источниковые форматы классов не стали ложной подсказкой.

**Подробно.** Единая схема http и удаление www применены к обоим классам и inference, чтобы уменьшить форматную подсказку источника. HTTPS-координата после этого постоянна. Это раскрытый компромисс; он не доказывает устранение всех source/path artifacts.

### 53. Чем публичные URL-признаки отличаются от модельных?

**Кратко.** Публичный wrapper исправляет часть reserved/IDNA логики, RF оставлен на замороженном v1.

**Подробно.** Public extractor уточняет reserved-суффиксы и Unicode-бренды; модель осталась на оценённом контракте v1. Для goggle.test brand_similarity различается. Тихая смена входов после test сделала бы старые метрики несоответствующими. Поэтому таблицу нельзя представлять точной атрибуцией RF.

### 54. Как считаются группы социальной инженерии?

**Кратко.** Regex ищет фразы, функция возвращает названия сработавших групп без повторов.

**Подробно.** matched_groups возвращает названия групп, а не каждое совпадение. k — число групп, S=min(k/3,1). Повтор «срочно» десять раз не даёт k10. Расширенный runtime-словарь отдельно от замороженного словаря ручных ML-признаков.

### 55. Почему без URL меняется знаменатель риска?

**Кратко.** Иначе отсутствующая ссылка искусственно понижала бы оценку.

**Подробно.** Отсутствующее P=None не является оценкой P0. Поэтому соответствующий вес убирается из суммы и знаменателя; при русском также отсутствует SMS-компонент. SE-компонент присутствует даже с нулём при отсутствии групп. Проверка if value вместо is not None была бы неверна.

### 56. Зачем overrides после формулы?

**Кратко.** Критические признаки задают нижнюю границу риска независимо от среднего.

**Подробно.** Среднее может разбавить сильный критический сигнал. Поэтому CODE_REQUEST задаёт минимум 70, сочетание двух сильных моделей 85, IP или Punycode с брендом 60. max только повышает риск. Это политика эвристической оценки, а не новая обученная вероятность.

### 57. Как FastAPI получает пользователя?

**Кратко.** Через Depends(current_user), который проверяет cookie-сессию в БД.

**Подробно.** Depends(current_user) получает cookie, хеширует token, находит AuthSession и проверяет expiry. Затем возвращается User. SQLAlchemy Session — соединённая единица работы с БД, AuthSession — строка авторизации; одинаковое слово session не означает один объект.

### 58. Что делает PBKDF2 и почему не обычный SHA?

**Кратко.** Многократно вычисляет производную ключа, замедляя перебор паролей.

**Подробно.** Пароль имеет невысокую энтропию, поэтому дорогая производная ключа затрудняет перебор. Salt делает одинаковые пароли разными хешами. Случайный token высокоэнтропийный, для его хранения подходит быстрый SHA256; переносить это решение на пароль нельзя.

### 59. Как реализован CSRF?

**Кратко.** Совпадение случайного cookie-токена и заголовка X-CSRF-Token.

**Подробно.** page ставит cookie и выводит token в meta. Браузерный api переносит его в заголовок; сервер сравнивает два значения. Запрос без соответствующего токена получает 403. SameSite и HttpOnly дополняют этот механизм, но не являются его синонимами.

### 60. Как исключается чужая история?

**Кратко.** В каждом серверном запросе есть условие Check.user_id==user.id.

**Подробно.** detail и remove выбирают запись одновременно по ID и user_id. history и clear_history также ограничены владельцем. Чужая запись возвращает 404. Ограничение только на уровне UI позволило бы обратиться к API напрямую и было бы нарушением контроля доступа.

### 61. Чем flush отличается от commit?

**Кратко.** flush отправляет изменения в транзакцию и даёт ID, commit фиксирует её.

**Подробно.** flush отправляет SQL в текущую транзакцию и выдаёт Check.id. Затем добавляются дочерние URL и признаки, commit фиксирует всё вместе. Rollback отменяет незавершённую работу. Несколько независимых commit могли бы оставить неполный результат.

### 62. Зачем unique(user_id, request_key)?

**Кратко.** Защищает от повторного создания одного результата, включая гонку запросов.

**Подробно.** Два запроса могут одновременно не увидеть существующей записи в предварительном select. Unique constraint решает гонку на уровне БД. При конфликте выполняется rollback и возвращается уже созданный результат. Это идемпотентность операции, не кеш всех одинаковых SMS.

### 63. Что создаёт Alembic?

**Кратко.** Версионированную схему таблиц и индексов.

**Подробно.** Миграция описывает создание семи таблиц и индексов, env.py подключает Base.metadata и параметры. Команда запуска применяет head. create_all в lifespan создаёт отсутствующее, но не заменяет эволюцию схемы. Downgrade на рабочей базе без цели выполнять нельзя.

### 64. Что сохраняется без согласия?

**Кратко.** input_text=NULL имаскированный ввод, плюс необходимые результаты.

**Подробно.** Полный текст отсутствует, но маскированный ввод и результаты остаются. mask_text скрывает телефон, карту и суммы, параметры URL внутри SMS тоже маскируются. Имена и другие слова могут сохраниться: это не полная анонимизация. Согласие относится к новым записям.

### 65. Как Dashboard считает значения?

**Кратко.** SQL GROUP BY/COUNT/AVG/date и join, а не перебор всех Check в Python.

**Подробно.** Сервер использует COUNT/GROUP BY/AVG/date и join, затем упаковывает агрегаты в JSON. Chart.js отвечает за отрисовку. Для admin all последние чужие записи не передаются: recent пуст. Период влияет на SQL-условие created_at.

### 66. Почему JS использует textContent?

**Кратко.** Чтобы введённая строка не интерпретировалась как HTML/скрипт.

**Подробно.** textContent помещает данные как текстовые узлы, не исполняемый HTML. Jinja2 также экранирует вывод. URL результатов не получают href. Сам JSON не защищает XSS, если потом вставить его содержимое через опасный HTML-метод.

### 67. Что делает fetch и как обрабатывается 204?

**Кратко.** Отправляет запрос; при 204 api возвращает null и не пытается читать JSON.

**Подробно.** 204 означает отсутствие тела: response.json здесь дал бы ошибку, поэтому api сразу возвращает null. Для остальных ответов JSON разбирается, плохой status становится Error с сообщением. finally снимает блокировку кнопки даже при ошибке.

### 68. Чем unit test отличается от integration test?

**Кратко.** Первый проверяет малую функцию, второй — взаимодействие компонентов.

**Подробно.** Unit-проверка изолирует функцию, integration соединяет HTTP, БД, авторизацию и модели. Fixture задаёт окружение, parametrize повторяет тест на разных данных, monkeypatch временно блокирует внешнее поведение. Утверждения assert должны проверять смысл, не только отсутствие исключения.

### 69. Что означает coverage78%?

**Кратко.** Выполнена примерно эта доля измеренных строк при тестах.

**Подробно.** Измерено 1479 statements и 323 miss при последнем аудите. Выполнение строки не доказывает правильность результата или полноту требований. ML около 71%, риск 98%; training CLI заметно слабее покрыты. Этот процент не является вероятностью отсутствия ошибок.

### 70. Какие логи безопасны?

**Кратко.** ID проверки, категория, времяобработки ислужебныеошибки безввода/секретов.

**Подробно.** perform пишет ID, категорию и duration; logging задаёт ротацию 1 MiB с пятью backup. Ввод SMS, пароли, токены и URL не должны попадать в логи. В команде запуска отключён access-log; debug-логирование request body на защите недопустимо.

## Сложные и каверзные:71–100

### 71. Можно ли обмануть систему?

**Кратко.** Да, правила и статистические модели допускают обходы и ошибки.

**Подробно.** Перефразирование, смешение букв, новые сокращения и смена распределения могут снизить сигнал. Char n-граммы и URL-флаги уменьшают лишь часть рисков. Для изучения нужны искусственные контрпримеры, а не реальные мошеннические кампании; гарантии против любого обхода нет.

### 72. Почему URL-модель хуже SMS-модели?

**Кратко.** Задачи, данные и представления различаются; фактически перенос на новые домены хуже.

**Подробно.** Факты:22 строковых признака, новые домены на test, сдвиг долей классов и падение метрик. Гипотезы: source/path bias и недостаточный сигнал. Нельзя объявить число признаков единственной причиной без эксперимента: SMS и URL — разные задачи и корпуса.

### 73. Почему нельзя изменить порог после test?

**Кратко.** Это адаптация решения к проверочным данным.

**Подробно.** После изменения по test он становится частью процесса выбора. Старую оценку нельзя продолжать считать независимой. Допустимо сформулировать гипотезы, затем нужен новый протокол и независимый final holdout. Удаление claim-файла методологию не исправляет.

### 74. Почему не переобучить на train+val и оставить старые метрики?

**Кратко.** Новый артефакт — уже другая модель.

**Подробно.** После refit меняются веса и сам артефакт; старый test оценивал другую модель. Больше данных может помочь, но не гарантирует качество. Здесь сохранён именно оценённый train-only объект, а отклонение от требования PDF явно раскрыто.

### 75. Не является ли EDA всего корпуса leakage?

**Кратко.** Описательный EDA до обучения отличается от выбора настроек по test, но требует дисциплины.

**Подробно.** PDF разрешает описательный анализ всего корпуса до обучения без подбора по test. Но выбор признаков или порога с оглядкой на тестовые шаблоны был бы адаптацией. Для будущих исследований разумнее train-only EDA и отдельный неприкосновенный holdout.

### 76. Почему калибровка сама может дать leakage?

**Кратко.** Если обучаемые признаки или сам classifier заранее видели calibrationfold.

**Подробно.** OOF должен быть невиденным для всего обучаемого преобразования, не только classifier. Глобальный IDF перед CV уже видел бы тексты calibration-fold. Поэтому SVM оборачивает полный FeatureUnion и scaler. Это архитектурная защита от утечки, а не следствие одного слова cv.

### 77. Доказывает ли ROC.996 безопасность всех SMS?

**Кратко.** Нет, это ранжирование на конкретном английском spamtest.

**Подробно.** AUC характеризует ранжирование на конкретных английских spam-примерах. Оно не измеряет подлинность отправителя или все виды fraud. Даже SMS-модель пропустила 5 из 93 positive; перенос на русский не доказан. Высокая метрика требует точного описания области действия.

### 78. Можно ли называть .99 вероятностью мошенничества 99%?

**Кратко.** Только с оговорками о целевой метке, распределении и калибровке.

**Подробно.** Вероятность относится к конкретной метке и распределению. Сдвиг prior и структуры примеров нарушает перенос шкалы; RF может ошибаться уверенно. В проекте нет отдельного reliability-анализа, поэтому .99 не нужно описывать как гарантированные 99% реального мошенничества.

### 79. Почему Precision падает при меньшей доле угроз?

**Кратко.** Среди большого числа безопасных даже небольшой FPR создаёт много ложных тревог.

**Подробно.** Precision=TPR·π/(TPR·π+FPR·(1−π)). При TPR.9, FPR.1,π.1 получаем.5. Сдвиг URL positive prior может объяснять часть падения Precision, но не всё ухудшение ROC: для него важна структура условных распределений.

### 80. Можно ли считать важность RF объяснением конкретного URL?

**Кратко.** Нет, глобальная importance не равна локальному причинному вкладу.

**Подробно.** Impurity importance — глобальное участие признака в уменьшении неоднородности. Конкретный прогноз зависит от путей и взаимодействий, а корреляции усложняют интерпретацию. Здесь публичная таблица ещё и отличается местами от v1-входов RF. Причинная атрибуция не реализована.

### 81. Почему unsafe URL не открывается, даже для проверки SSL?

**Кратко.** Политика проекта — исключительно строковый анализ, без сетевых запросов.

**Подробно.** Проверка сертификата, DNS или редиректа добавила бы сетевой доступ и риски SSRF/приватности. Политика проекта — строковый анализ. HTTPS-флаг читается из scheme и не подтверждает действительный сертификат; сокращатель также не раскрывается переходом.

### 82. Всегда ли Punycode опасен?

**Кратко.** Нет, это законный способ записать международный домен ASCII-символами.

**Подробно.** Punycode кодирует допустимые международные домены. Опасность подозревается по сочетанию маскировки бренда, смешения букв и других сигналов. Запрет всех IDN давал бы ложные тревоги. В проекте сочетание Punycode+brand повышает риск, но не является репутационным фактом.

### 83. Почему самостоятельный URL и тот же URL в SMS могут дать разный общий score?

**Кратко.** В SMS есть дополнительные текстовые и словарные сигналы; standalone использует отдельное отображение диапазонов.

**Подробно.** В SMS действуют текст, SE и взвешенная формула. Standalone URL использует дополнительное отображение t1/t2 в уровни, чтобы категория не разбавлялась отсутствующим SMS. Это специальный контракт эвристики, не единая обученная модель вероятности.

### 84. Что если URL-флаг есть, а общая причина сообщает об отсутствии угрозы?

**Кратко.** Это известный пробел объяснений, не доказательство отсутствия флагов.

**Подробно.** Общий compute_risk не переносит все причины shortener/@/TLD из URL-блока. Поэтому возможен противоречивый fallback. Флаги видны отдельно, но это не закрывает требование полноты общих причин. Пробел нужно признать, а не трактовать fallback как доказательство безопасности.

### 85. Почему русский Recall .66 не позволяет заявить полную поддержку?

**Кратко.** Он ниже языкового ориентира.80 и получен на небольшом искусственном корпусе.

**Подробно.** Recall.66 ниже ориентира.80, корпус мал и размечен AI. Даже более высокая цифра на тех же 100 искусственных сообщений не заменила бы независимую репрезентативную оценку. Сейчас используется rules+URL, обученного русского SMS classifier нет.

### 86. Использовался ли русский test повторно для настройки правил?

**Кратко.** По протоколу его не использовали для обучения или настройки.

**Подробно.** Согласно зафиксированному протоколу, словарь, модели и пороги были заморожены до проверки. Нельзя затем менять правила по ошибкам того же набора и оставлять результат как независимый. Для будущей русской калибровки нужны отдельные данные.

### 87. Надёжно ли простое определение языка?

**Кратко.** Он достаточен для простого маршрутизирования, но не для всех смешанных/обфусцированных сообщений.

**Подробно.** Любая русская кириллица даёт ru; иначе латиница даёт en, иначе other. Смешанные языки, транслитерация и текст адреса могут влиять на выбор. Это эвристика маршрутизации, не полнофункциональная языковая модель. Её следует показать непосредственно в analyze.

### 88. Достаточно ли HttpOnly для защиты от XSS?

**Кратко.** Нет, скрипт может выполнять действия в origin даже без чтения cookie.

**Подробно.** XSS-скрипт в своём origin может отправлять действия от имени пользователя, даже не читая cookie. Нужны экранирование и безопасное построение DOM. HttpOnly уменьшает кражу токена, но не решает весь XSS. CSRF тоже не лечит уже исполняющийся скрипт.

### 89. Может ли ORM допустить SQL injection?

**Кратко.** Да, если разработчик строит сырой SQL конкатенацией.

**Подробно.** ORM безопасно передаёт параметры в проверяемых выражениях select/where. Но разработчик мог бы вручную склеить SQL и нарушить эту гарантию. Поэтому надо рассматривать реальные вызовы и тесты, а не говорить, что название библиотеки исключает любой SQL injection.

### 90. Почему не JWT?

**Кратко.** Непрозрачные серверные сессии проще отзывать в локальном монолите.

**Подробно.** Серверные opaque sessions легко отзывать удалением строки. JWT — подписанный токен с данными — потребовал бы проверки подписи, expiry и стратегии отзыва. Для локального монолита JWT не обязателен, его отсутствие не означает слабую авторизацию само по себе.

### 91. Что произойдёт при двух workers?

**Кратко.** Модели загрузятся в каждом, а лимиты в памяти станут раздельными.

**Подробно.** Каждый worker загрузит свои модели и отдельные limiter в памяти. SQLite останется общим файлом с ограничениями записей. Поэтому глобальный 30/min не гарантируется. Масштабирование требует общего хранилища лимитов и отдельных нагрузочных проверок.

### 92. Всегда ли async ускоряет ML?

**Кратко.** Нет, CPU-bound синхронный вызов блокирует обработку в своём event loop.

**Подробно.** await освобождает ожидание подходящего I/O, но синхронный predict_proba не становится неблокирующим. Текущий код в async-обработчике выполняет ML и SQL синхронно. Следующее масштабирование потребовало бы обоснованного пула или очереди, а не механической добавки async.

### 93. Почему hash модели недостаточен для доверия?

**Кратко.** Злоумышленник может заменить и joblib, и его sidecarhash.

**Подробно.** Заменив sidecar вместе с моделью, атакующий может указать новый корректный hash. SHA проверяет целостность относительно ожидания, не издателя. joblib может исполнять код при загрузке; доверенный источник обязателен. Подписанных манифестов проект не реализует.

### 94. Полностью ли анонимен маскированный SMS?

**Кратко.** Нет, остаются слова, имена и другие возможные личные сведения.

**Подробно.** mask_text не распознаёт все личные сведения: остаются имена и произвольные слова. Consentfalse означает отсутствие полного input_text, а не отсутствие хранения вообще. Сохраняются маскированный текст и результаты; удаление собственной истории поэтому важно.

### 95. Почему 114 тестов не равны 40 приёмочным кейсам?

**Кратко.** Параметризованные исполнения и формальный каталог имеют разные структуры.

**Подробно.** PDF требует предусловия, шаги, вход, ожидание, факт и трассировку каждого ФТ/НФТ. Pytest items, включая параметризацию, не дают автоматически оформленного каталога. Зелёный запуск подтверждает реализованные проверки, а не весь формат академической сдачи.

### 96. Гарантирует ли coverage98% отсутствие ошибок риска?

**Кратко.** Нет, строка может быть выполнена, но неправильность не проверена assert.

**Подробно.** Одна строка может выполниться без проверки правильности её результата. Высокий coverage не исключает ошибок взаимодействий и неполного соответствия требованиям. Пропуски URL-причин при 98% риска — конкретный пример этой разницы.

### 97. Почему API .021 с не подтверждает Dashboard≤2 с?

**Кратко.** Браузер ещё должен загрузить ресурсы и выполнить отрисовку.

**Подробно.** Полное время включает ресурсы, JavaScript, layout и render Chart.js. API benchmark измеряет только серверную часть сценария. В нём 1000 строк,900 — явные нагрузочные фикстуры, не выдуманные предсказания. Полный браузерный замер ещё нужен.

### 98. Почему сохранённые метрики notebook не являются заглушкой приложения?

**Кратко.** Notebook показывает фиксированный эксперимент, а веб-анализ вычисляет новый прогноз.

**Подробно.** Отчёт эксперимента закономерно хранит фиксированные метрики. Веб-сервис для нового текста вызывает ModelStore.predict, а не lookup готовой категории. Обучать при каждом показе не требуется и опасно для протокола. Незнакомый искусственный пример помогает показать реальный inference.

### 99. Как правильно улучшать проект после аудита?

**Кратко.** Сначала определить новый протокол и независимую оценку, затем менять код или модель.

**Подробно.** Разделить исправления UI/контрактов и изменения модельных признаков. Сохранить старые отчёты, версионировать артефакты, сформировать новый независимый holdout. Для русского нужны данные, для URL — исследование смещения; старый test нельзя использовать для нового выбора.

### 100. Что отвечать на замечание «проект не закончен»?

**Кратко.** Да, академическая приёмка частичная, но основные пользовательские сценарии работают.

**Подробно.** Признать частичную академическую приёмку и показать работающий сквозной сервис, доказательства и конкретные долги. Не скрывать URL false positive и русский Recall.66. Сильный ответ объясняет границы и корректный план исследований, а не обещает 100% соответствие.
